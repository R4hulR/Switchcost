## 2026-09-17 (cont. 2) — Independent raw-log review: six fixes, calibration, matched sweep, review bundle

An independent review of the smoke-test raw logs (not from this session) found six real problems, all confirmed by inspecting the actual code/data rather than taken on faith. Fixed all six, added a dedicated IPC-floor measurement, then ran the calibration + matched-sweep phases the pilot design calls for. Full technical detail of each fix is in `docs/pilot_config_matrix.md` (§7, §9, §11, §5) inline at the point each correction applies; summarized here:

1. **Percentile convention** was undocumented nearest-rank (`sorted[int(n*p)]`), differing from standard linear interpolation by up to 2.2ms at p99 on a 200-row sample. Centralized in `scripts/common/stats.py` (numpy `'linear'` method), used everywhere, `percentile_method` recorded in every summary.
2. **Timeout semantics bug**: the queue-timeout check compared `execution_start` against `scheduled_arrival` instead of `enqueue_ts`, silently folding generator delay into what was meant to be a pure queue-wait bound (review found 39/71 `TIMED_OUT` requests had actually waited <50ms in queue once generator delay was excluded). Fixed by giving each `Task` its own `enqueue_ts` and checking against that. Verified on a fresh overload run: 0/98 `TIMED_OUT` requests now have queue-wait under the threshold.
3. **Mislabeled "IPC floor"**: a loaded run's `queueing_delay` p50 (37ms, 496ms under overload) was being reported as an IPC-floor estimate, which is only valid near-idle. Removed from the summary; added `scripts/measure_ipc_floor.py`, a dedicated unloaded measurement (one worker, sparse single requests) — actual floor ≈2.4–2.5ms p50.
4. **Shutdown accounting**: making the collector thread daemon (previous fix) stopped the hang but didn't confirm collection. Orderly shutdowns now actively wait (`wait_for_collection`) for every enqueued request's result to be read, not just assumed after a fixed grace period. Forced terminations now write worker status directly to `multiprocessing.Array` shared memory (bypassing the queue, which can lose messages under `SIGTERM`) so "missing a Result" can be resolved into `UNFINISHED` (confirmed never dequeued), `INTERRUPTED` (confirmed mid-flight, true outcome unknown), or `COMPLETED_UNCONFIRMED`/`TIMED_OUT_UNCONFIRMED` (worker finished locally, only the message was lost) instead of one undifferentiated bucket. Verified: a forced-termination test produced 8 confirmed `INTERRUPTED` + 468 confirmed `UNFINISHED`, distinctly labeled.
5. **Missing measurements**: peak RSS was null because it was read after the worker process had already exited (the `/proc` entry was gone). Fixed with a background thread that polls `/proc/<pid>/status` while workers are alive and tracks the max. Added generator-delay percentiles, explicit measurement-window boundaries, achieved arrival rate, throughput with an explicit window definition, resolved per-worker runtime settings (actual `intra_op_num_threads`/execution mode/spinning flags/providers, not just what was requested), and enqueue-attempt timestamps for `REJECTED` requests.
6. **Arrival-duration mismatch**: schedule generation fixed the request count to `round(rate*duration)` and let Poisson gaps sum to whatever they summed to, so a nominal "10s" run could realize 9.3s. Switched `build_schedule` to duration-bounded generation (stop once the running sum would exceed the target), so the realized span is now ≤ the nominal duration by construction; both nominal and realized values are reported.

**Verification rerun** (`results/verification/`): re-ran the normal-load, overload, and forced-drain-timeout smoke scenarios against the fixed code. All six fixes confirmed working as intended (see bundle `REVIEW.md` for exact numbers) before proceeding to calibration.

**Calibration** (`scripts/run_calibration.py`, `results/calibration/`, tuning split): 5 rates × 4 configs, 6s probes. Found real, differentiated saturation points: W1T8 saturates ~100-150 req/s (throughput plateaus ~117/s), W2T4 ~150-220 req/s (plateaus ~181/s), W4T2 and W8T1 not saturated by 220 req/s. **Notable finding, not assumed going in**: at low load (rate=30), e2e p50 latency is *lowest* for W1T8 (12.6ms) and increases monotonically with worker count — the opposite ranking from capacity. This is the fewer-workers-more-threads vs. more-workers-fewer-threads trade-off the research question is actually about, observed directly rather than hypothesized. Froze a common rate set from this data: low=40, medium=90, stress=130 req/s (reasoning in `results/calibration/calibration_decision.json`).

**Matched fixed-config sweep** (`scripts/run_sweep.py`, `results/sweep/`, eval split): 3 rates × 4 configs × 3 repeats = 36 runs, identical frozen arrival schedule per rate replayed across all 4 configs, run order randomized (seed 777). All 36 runs completed with `orderly_shutdown: true` and `collection_confirmed: true`. **Result: the crossover is real but asymmetric, not clean.** W1T8 only wins by ~1-8ms at low load, and is already behind W2T4 on p99 even there (29.4-32.2ms vs 22.0-22.8ms). By medium load W2T4 has overtaken it outright. At stress load W1T8 collapses by ~30-50x (p50 474.8-732.8ms) while W2T4/W4T2/W8T1 all stay close to their low-load numbers. It also means criterion 3 (room above a strong fixed baseline) is now the load-bearing open question, not yet answered — a strong-fixed-config baseline (i.e., just always running W2T4) hasn't been run head-to-head against anything yet, since there's no adaptive policy to compare it to at this stage.

This is now the primary comparison for the pilot going forward, and `results/REVIEW.md` needs correcting.

**Five fixes, in order applied:**

1. **NPZ lazy-loading overhead was inside the timed request loop.** `np.load()` returns a lazy `NpzFile`; every `data["key"]` access re-reads/re-decodes that archive member. Fixed by materializing into plain ndarrays once, up front, in both `smoke_bench.py` and `measure_ipc_floor.py`. Also restructured the generator loop so payload slicing happens *before* `enqueue_ts` is stamped (previously it happened inside `Task(...)` construction, after the timestamp — inflating queueing_delay with generator-side prep time). **Measured effect, not just theoretical**: re-ran `measure_ipc_floor.py` after the fix — the "floor" dropped from ~2.4ms to ~1.04ms p50, confirming roughly 1.4ms of the old number was NPZ-decode overhead, not IPC. Added a direct pickle-roundtrip-only microbenchmark (~0.07ms p50) to further decompose serialization cost from pipe-transfer/wake-up/unpickle overhead, and stopped calling any of this "pure IPC" (now labeled "IPC + queue wake-up overhead").
2. **Generator-process background threads (collector, resource-monitor, and `task_queue`'s own feeder thread) were never pinned or verified** — only the main thread was, via `os.sched_setaffinity(0, ...)`, which only affects the calling thread. Checked and found REAL violations, not hypothetical: on a fresh verification run, the collector thread and resource-monitor thread both showed full `0-39` affinity, contaminating the CPUs 8-11 generator budget. Fixed with a new `common.affinity.verify_and_repin_all_threads()` helper (factored out of the pattern `worker.py` already used), called twice — before the generator loop (catches main/collector/monitor) and after (catches the task_queue feeder thread, which only exists once something has been `put()` to it). Confirmed fixed: post-fix violations = 0 both times on the same verification run. Unresolved violations (worker OR generator) now set `run_valid: false` in the summary and exit the harness with code 2, rather than only printing a warning — `run_calibration.py`/`run_sweep.py` treat a nonzero exit as a hard failure already.
3. **Forced-shutdown status writes were in the wrong order.** `shared_status[...] = STATUS_COMPLETED` was written *before* `shared_completion[...] = completion_ts` — a kill between those two lines would have left a status claiming a valid timestamp that was actually still the uninitialized array default (0.0). Fixed by writing data before the flag everywhere (renamed `STATUS_STARTED` → `STATUS_DEQUEUED` for clarity in the process). Shared timestamp arrays now default-initialize to an explicit `-1.0` sentinel (not `0.0`, which could be mistaken for a real value) and reconciliation validates recovered records (timestamps present and monotonically ordered) before trusting them — a validation failure downgrades to a new `UNKNOWN` outcome rather than reporting a bogus latency. `UNFINISHED` is now described as "not observed as dequeued," not "confirmed never dequeued" — there's an irreducible microsecond-scale race between `task_queue.get()` returning and the `STATUS_DEQUEUED` write that can't be fully closed, and the report no longer overclaims certainty it doesn't have. Worker exit codes are now checked (`p.exitcode`); a non-zero, non-SIGTERM exit downgrades `orderly_shutdown` even though `is_alive()` alone wouldn't catch a crash. Sentinel insertion (`task_queue.put(None)`) is now timeout-bounded against the drain deadline — an unbounded blocking put on a still-full queue could previously hang before the deadline was ever enforced, a second (distinct) hang risk from the one fixed in round 1.
4. **Rate/duration reporting still conflated two different things.** `achieved_arrival_rate_hz` is now explicitly `n_requests / duration_s_nominal` (matches the reviewer's requested framing), and `last_arrival_offset_s` (the realized schedule span, which a bounded Poisson process need not make exactly equal to the nominal duration) is now reported as its own separate field rather than used as the rate's denominator.
5. **Throughput conflated in-window and drain-time completions into one number.** Now reported as two explicit fields: `completed_within_nominal_window` (only completions with `completion_ts` inside the nominal duration) and `completed_including_drain` (all completions, including post-window stragglers).

## 2026-09-17 (cont. 4) — Third review: recheck independently confirmed, time-varying fixed-config traces

An independent review checked all 95,226 recheck requests directly (counts, percentiles, timestamp ordering, in-window throughput, matched schedules) and confirmed they agree with what was reported. **Go/no-go criterion 1 now passes provisionally for this workload and this WSL environment.** Instruction was to proceed to time-varying traffic against the two fixed configs (W2T4, W4T2) — still explicitly no switching/controller — before touching transition costs or baselines.

**One small correction applied first** (item 7 of the review): `run_recheck.py`'s docstring claimed 5% duration padding "guarantees" ≥5,000 requests "by construction" — wrong, a bounded Poisson process's request count has real variance, padding only makes the target *likely*. All 18 recheck runs did in fact exceed 5,000 (5,128-5,455), which is now stated as an observed fact, not a guaranteed property; `run_one()` in that script now validates the actual count post-hoc and warns if a future run falls short.

**Harness extended for time-varying traces** (`scripts/common/trace.py`, new; `scripts/smoke_bench.py`, extended):
- A trace is a saved JSON file: a list of phases (`phase_id`, `rate_hz`, `duration_s`, each getting its own independent Poisson process via a deterministic per-phase seed) concatenated into one globally-ordered arrival schedule, computed once via `build_phased_schedule()` and written to disk (`save_trace`/`load_trace`) — replaying it against multiple configs means loading the identical file, not trusting RNG reproducibility across separate invocations, per the review's "replay a saved arrival-offset trace" instruction.
- `smoke_bench.py --trace-file PATH` replays the whole concatenated schedule as **one continuous run**: workers and queues are spawned once and stay alive across every phase boundary; nothing about a phase transition triggers a drain, restart, or re-warm (this falls out naturally from reusing the same single generator loop and single worker pool across the whole concatenated offset list — no special-casing was needed to satisfy this requirement).
- Every raw row now also carries `phase_id` — attributed by **scheduled** arrival offset (the phase a request's offset fell into at trace-build time), not by whichever phase happened to be running when it was actually dequeued/executed, so a request delayed across a phase boundary by backlog is still correctly attributed to the phase it was scheduled in — and `input_id` (`request_id % n_pool`, the corpus sentence actually used).
- The run summary now reports `latency_ms_by_phase`, `outcome_counts_by_phase`, and `throughput_by_phase`, each computed **independently from that phase's own filtered raw rows** — never by averaging a phase's percentile into the whole-trace number or vice versa (the review's explicit "never average phase p99 values to estimate whole-trace p99" was respected by construction: the whole-trace `latency_ms.e2e` block already summarized ALL completed rows directly, unchanged from before; the per-phase blocks are a separate, independent computation added alongside it, not derived from it).
- Backward compatibility: when `--trace-file` isn't given, the existing `--rate/--duration/--arrival` single-phase CLI behavior is preserved exactly, internally represented as a one-phase trace (`phase_id="main"`) so the same code path handles both — `run_calibration.py`, `run_sweep.py`, and `run_recheck.py` needed no changes.

**Deadline sensitivity set, frozen before any of the new runs** (`results/time_varying/deadline_set.json`): {25, 50, 100}ms, chosen from already-collected recheck data (not the runs about to be measured) to span tight/moderate/loose relative to the observed W2T4/W4T2 p99 range — reasoning for each threshold recorded in the file. Missed-deadline fraction defined as `n_missed / n_offered` where `n_offered` is every scheduled request including rejected/timed-out/unfinished/etc. (computed in `scripts/analyze_time_varying.py`, applied post-hoc to the raw CSVs, kept out of the harness itself since deadline evaluation is an analysis concern, not something the harness needs to know about to run correctly).

**Experiments run** (`scripts/run_time_varying.py`, 12 runs, ~24 minutes wall-clock, background):
- **Sustained low-high-low**: 40 → 130 → 40 req/s, phases 50s/40s/50s, 2 fresh seeds (40001-40002, not reused from the sweep's 5001-5003 or the recheck's 20001-20003).
- **Repeated short bursts**: baseline 40 req/s, bursts at 130 req/s, durations {0.1, 0.5, 2, 10}s (10 repeats for the three shorter durations, 5 for 10s since it already carries far more samples per instance — gap between bursts sized `max(5, 2×duration)` to let the queue drain back to baseline before the next one), one fresh seed (41001) per duration, matched across both configs.
- All 12 runs: `run_valid: true`, 100% `COMPLETED`, zero rejections/timeouts/unfinished at these particular loads.

**Findings** (full numbers in `results/REVIEW.md` §7, plots `sustained_by_phase.png`/`burst_p99_by_duration.png`):
- Sustained trace: W2T4 wins p99 in both low phases (before *and* after the spike: 22.0-23.2ms / 21.2-21.8ms), W4T2 wins p99 dramatically during the spike itself (30.3-30.4ms vs. W2T4's 49.4-68.9ms). **No visible carryover effect** — the post-spike "low2" phase's p50/p99 are close to the pre-spike "low1" phase's for both configs (no formal significance test was run), i.e. neither config shows an obvious lingering effect from the preceding high-load phase within the 50s recovery window tested. At the 50ms deadline (chosen specifically to separate the two configs), W4T2 has essentially zero whole-trace misses while W2T4 still misses 0.5-1.3% of *all offered* requests.
- Burst trace: pooling all repeated-burst-window requests per duration (114 to 6,412 pooled samples depending on duration — reported explicitly, not presented as if from a single burst), W4T2's pooled p99 stays flat (~24-29ms) across every duration tested; W2T4's is 2-3x worse at every duration, peaking at the 2s burst (76.2ms) and easing somewhat by 10s (46.8ms) — plausibly because a 10s burst gives W2T4 enough time to settle into a new (still worse, but less transient) quasi-steady-state, while 0.5-2s bursts catch it mid-transient. This non-monotonic pattern is noted as an open question in the review bundle, not fully explained.
- **The confirmed crossover extends from steady-state to time-varying traffic** — not an artifact of the fixed-rate sweep design specifically. Still no evidence on whether adaptation could beat always-W4T2 (which now looks like the stronger baseline for a deadline-oriented framing) — that's next: transition-cost measurement, then a real comparison against both fixed baselines. No adaptive controller has been built.

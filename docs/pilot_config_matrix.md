# Pilot Configuration Matrix (v1 — proposal)

Date: 2026-09-17
Depends on: `environment_report.md`

This is the concrete first pilot: smallest set of configurations that can answer "do different worker/thread configurations win under different traffic, and does switching between them cost anything measurable." No adaptive controller yet.

## Round 2 corrections (2026-09-17), from a second independent review

Applied after round 1's six fixes and the first calibration+sweep phase. Full detail in `docs/research_log.md`'s third 2026-09-17 entry and `results/REVIEW.md`; summarized here since they touch several sections below:

1. **NPZ arrays are now materialized into plain in-memory ndarrays once, up front** (`scripts/smoke_bench.py`, `scripts/measure_ipc_floor.py`) — `np.load()`'s lazy `NpzFile` re-decodes an archive member on every access, which was real, avoidable overhead previously happening inside the timed per-request loop. Payload slices are now prepared *before* `enqueue_ts` is stamped, not during `Task` construction after the timestamp — isolates input-prep time from IPC/queueing delay (`input_prep_ms`, now its own reported bucket, confirmed negligible: ~0.01-0.02ms p50 once materialized).
2. **The "IPC floor" is re-measured and no longer called pure IPC.** With materialized arrays the unloaded floor dropped from ~2.4ms to ~1.0ms p50 (the earlier number included real NPZ-decode overhead, not just IPC) — and `scripts/measure_ipc_floor.py` now also runs a direct in-process pickle-roundtrip microbenchmark (~0.07ms p50) to decompose serialization cost from the remaining pipe-transfer/OS-wake-up/unpickle overhead, rather than reporting one undifferentiated number.
3. **Every generator-process thread is now pinned and verified, not just the main thread.** `os.sched_setaffinity(0, ...)` only affects the calling thread; the collector, resource-monitor, and (once it exists, later in the run) `task_queue`'s own feeder thread were previously unchecked and, when checked, turned out to actually have full unrestricted affinity — a real, confirmed contamination of the dedicated server/generator CPU split, not a hypothetical risk. Fixed with `common.affinity.verify_and_repin_all_threads`, run twice (before and after the generator loop). Unresolved violations (worker or generator) now set `run_valid: false` and exit the harness with code 2, rather than only printing a warning.
4. **Forced-shutdown reconciliation is more conservative.** Every shared-memory status write now happens strictly *after* its corresponding timestamp is written ("data before flag"), closing a real bug where `STATUS_COMPLETED` could be observed with an uninitialized completion timestamp if a kill landed between the two writes in the wrong order. Recovered records are validated (timestamps present and monotonically ordered) before being trusted; a validation failure downgrades the outcome to `UNKNOWN` instead of reporting a bogus latency. `UNFINISHED` is now reported as "not observed as dequeued" rather than "confirmed never dequeued," since an irreducible microsecond-scale race remains. Worker exit codes are checked (`worker_exit_codes` in the summary) — a nonzero, non-SIGTERM exit downgrades `orderly_shutdown` even if `is_alive()` alone wouldn't have caught it. Sentinel insertion (`task_queue.put(None)`) is now timeout-bounded, since an unbounded blocking put on a still-full queue could previously hang before the drain deadline was ever enforced.
5. **Rate/throughput reporting is split into what was actually asked for.** `achieved_arrival_rate_hz_over_nominal_duration` (= N / nominal duration) and `last_arrival_offset_s` (the realized schedule span, which a bounded Poisson process need not make equal to the nominal duration) are now separate fields instead of one derived from the other. Throughput is reported as two explicit numbers: `completed_within_nominal_window` (only completions landing inside the nominal duration) and `completed_including_drain` (all completions, including post-window stragglers) — the earlier single number conflated the two.

## Round 2 empirical correction: W2T4 does not dominate tail latency

The round-1 sweep's summary claimed W2T4 looked like a uniformly "robust default." A closer look at p99 specifically (not just p50) shows a real crossover **between W2T4 and W4T2**: W2T4 wins p99 at the low rate (40 req/s), W4T2 wins p99 at medium and stress rates (90 and 130 req/s). Confirmed and strengthened by a dedicated recheck (3 fresh seeds, ≥5,000 requests/condition) — see `results/REVIEW.md`. This is now the primary comparison for the time-varying phase below.

## Round 3 additions (2026-09-17): time-varying fixed-config traces, no switching yet

A third independent review, after confirming the round-2 fixes and the W2T4-vs-W4T2 crossover held up (95,226 recheck requests independently checked: counts, percentiles, timestamp ordering, in-window throughput, matched schedules all agreed — criterion 1 passes provisionally for this workload and WSL environment), asked for **time-varying traffic against fixed configs, still no adaptive switching**, to see how W2T4 and W4T2 behave under load *changes*, not just steady different loads.

**Harness extension** (`scripts/common/trace.py`, `scripts/smoke_bench.py --trace-file`): a trace is a saved JSON file — a list of phases (`phase_id`, `rate_hz`, `duration_s`, each with its own independent Poisson process) concatenated into one globally-ordered arrival schedule, computed once and written to disk so replaying it against multiple configs means loading the identical file, not trusting RNG-reproducibility across invocations. `smoke_bench.py` replays the whole concatenated schedule as **one continuous run** — workers and queues spawned once, kept alive across every phase boundary, drained/shut down only at the very end; nothing in the phase transition itself triggers a drain, restart, or re-warm. Every raw request row now also carries `phase_id` (attributed by **scheduled** arrival time — the phase the request's offset fell into at trace-build time, not whichever phase happened to be running when it was actually dequeued/executed, so a request delayed across a phase boundary by backlog is still attributed to the phase it was scheduled in) and `input_id` (the corpus sentence index used, `request_id % n_pool`). The run summary reports per-phase latency/outcome/throughput (`latency_ms_by_phase`, `outcome_counts_by_phase`, `throughput_by_phase`) **computed independently from the raw rows for that phase** alongside the existing whole-trace numbers — never derived by averaging phase values into a whole-trace number or vice versa.

**Two trace types** (`scripts/run_time_varying.py`), both replayed identically (same trace file) against W2T4 and W4T2:
- **Sustained low-high-low**: 40 → 130 → 40 req/s, phases 50s/40s/50s, 2 fresh seeds (40001-40002, not reused from the sweep's 5001-5003 or the recheck's 20001-20003).
- **Short bursts**: baseline 40 req/s punctuated by repeated bursts at 130 req/s, at durations {0.1, 0.5, 2, 10}s (10 repeats each for the three shorter durations, 5 for 10s since it already carries far more samples per instance), gap between bursts sized to let the queue fully drain back to baseline first. One fresh seed (41001) per duration, matched across configs.

**Pooled burst analysis, not per-instance** (`scripts/analyze_time_varying.py`): a single 0.1s burst at 130 req/s only contains ~13 requests — nowhere near enough for its own percentile. Requests from all repeated burst instances of the same duration are pooled together (grouped by phase-id prefix, e.g. every `burst_0`, `burst_1`, ... `burst_9`) before computing a percentile, and the pooled sample count is reported alongside it rather than presenting a percentile from a handful of requests. Baseline-phase requests are pooled the same way as a reference.

**Deadline sensitivity set, frozen before these runs** (`results/time_varying/deadline_set.json`): {25, 50, 100}ms, chosen from already-collected recheck data (not the runs they're applied to) to span tight/moderate/loose relative to the observed W2T4/W4T2 p99 range. Missed-deadline fraction = `n_missed / n_offered`, where `n_offered` is **every scheduled request including rejected/timed-out/unfinished/etc.** (not just the completed subset) and a completed request counts as missed if its e2e latency exceeds the threshold. Not adjusted after seeing results.

Still no switching/controller — this phase only measures how the two fixed baselines behave on time-varying traces, to inform whether adaptation has anything to work with beyond what's already known from steady-state traffic.

## 3. CPU budget and pinning plan

Verified from the environment report: `taskset` affinity is honored, HT sibling pairing is real and consistent (`cpu0,1` → core 0; `cpu2,3` → core 1; etc.), no cgroup CPU quota is active, all 40 logical CPUs are available.

- **Server CPU budget: 8 guest logical CPUs — CPUs 0–7.** Fixed across all configs in this matrix so comparisons are apples-to-apples. Per the corrected environment report §3, these are **guest-scheduler** slots, not a confirmed physical-core assignment: WSL2's sibling-pairing (0-1, 2-3, ...) is internally consistent but not verified to correspond to real hardware thread pairs, and guest affinity does not guarantee physical isolation — the Hyper-V host can still time-slice these guest CPUs against Windows and other guest CPUs at the physical layer.
- **Load generator: CPUs 8–11, pinned separately from the server's guest CPUs** — this separates them at the guest-scheduling level (the generator's threads can't be scheduled onto the same guest CPU as a server worker), which is the level of isolation actually available here. It is **not** a guarantee of physical isolation between generator and server load (see above) — that caveat is carried into every result, not resolved by this pinning.
- **CPUs 12–39: left free** for WSL/host background activity; `/proc/loadavg` and `free -h` will be snapshotted before/after each run and logged, since this is a shared VM, not an isolated box (see environment report §8).

## 4. Worker/thread configurations (fixed CPU budget = 8)

All four configurations use exactly 8 logical CPUs total, factored differently between process-level parallelism (workers) and intra-op thread-level parallelism (threads per worker). `inter_op_num_threads = 1` for every config (single mostly-sequential embedding graph — inter-op parallelism isn't expected to matter here, and fixing it removes a dimension; will revisit only if evidence suggests otherwise).

| Config ID | Workers (processes) | Intra-op threads/worker | CPU pinning |
|---|---|---|---|
| W1T8 | 1 | 8 | worker 0 → CPUs 0-7 |
| W2T4 | 2 | 4 | worker 0 → CPUs 0-3, worker 1 → CPUs 4-7 |
| W4T2 | 4 | 2 | worker N → CPUs [2N, 2N+1] |
| W8T1 | 8 | 1 | worker N → CPU N |

- Each "worker" = a separate OS process, each with its own `onnxruntime.InferenceSession` (one model copy each — memory cost tracked, see §7). Using separate processes rather than threads-in-one-process sidesteps Python-level contention and matches how a real multi-worker inference server would be deployed.
- **Queue design (corrected): one shared FIFO queue, not per-worker round-robin, for the initial comparison.** A single shared queue consumed by whichever worker in the config is free removes routing-policy choice as a confound — if per-worker round-robin queues were used instead, an apparent win for one config could actually be an artifact of lucky/unlucky static routing (e.g., one worker's queue running dry while another backs up) rather than the worker/thread factorization itself. Implementation: a single `multiprocessing.Queue` (approximately FIFO — CPython's `multiprocessing.Queue` uses an internal feeder thread and pipe, so strict global FIFO order under concurrent `put`s from one generator is expected but not guaranteed by the stdlib docs; this will be checked empirically in the smoke test by verifying dequeue order matches enqueue order under the actual load levels used, and logged if violated) shared by all of a config's workers, each pulling the next available request when idle. Per-worker round-robin is deferred; if it's used later for a specific reason, worker-level imbalance (queue depth/idle time per worker) will be measured and reported explicitly, and routing will be ruled out as the explanation for any observed win before attributing it to the worker/thread factorization.
- Batch size fixed at **1** (one request = one embedding call) for the whole pilot, per the brief.
- Input sequence length: will be **fixed to a single representative token length** (exact value chosen after inspecting the input corpus — likely truncate/pad to a fixed length) rather than left to vary, so sequence-length variance doesn't become an uncontrolled second tuning dimension alongside worker/thread count. This mirrors the brief's fixed-batch-size rationale.
- Corpus: a fixed sentence set will be split up front into a **tuning subset** and a **held-out evaluation subset**. This alone is not sufficient for workload generalization (see §5a) — the traffic *pattern* (arrival rates/seeds) is split the same way.

## 5. Traffic patterns (open-loop arrivals)

All request arrivals are scheduled on a fixed clock independent of server completions (open-loop), per the measurement requirements. Four timestamps recorded per request: scheduled arrival, actual enqueue, execution start, completion (timing boundary defined precisely in §9). Load-generator-side scheduling delay (actual enqueue − scheduled arrival) is logged explicitly so generator saturation is visible and never misread as server latency.

**Corrected: rates are calibrated once, then frozen as an absolute, shared schedule replayed identically across all 4 configs — not re-derived as a percentage of each config's own capacity.** The original plan risked an apples-to-oranges comparison: if each config were tested at, say, "50% of its own max throughput," two configs could receive completely different absolute request rates and never be compared under the same offered load. Corrected procedure:

1. **Tuning phase**: run short calibration probes against the tuning corpus/config combinations to find the approximate max sustainable throughput *across* the 4 configs (i.e., bounded by whichever config saturates first). This phase's numbers are for calibration only and are not reported as pilot results.
2. **Freeze a common rate set**: pick a small set of absolute arrival rates (e.g., low / medium / near-saturation, spaced relative to the *slowest* config's measured capacity so all 4 configs are exercised at genuinely comparable offered load, including at least one rate that saturates the slowest config and is still sub-saturating for the fastest — that gap is exactly what would let different configs "win" differently).
3. **Freeze arrival schedules and inputs**: generate the actual sequence of (scheduled-arrival-timestamp, request-input) pairs once per traffic pattern × rate combination (using a fixed random seed), and **replay the identical schedule** against every one of the 4 configs. Same requests, same timing, same order, only the server config differs — isolating the config as the only varying factor. **Schedule generation is duration-bounded, not count-bounded** (corrected 2026-09-17: an earlier version fixed the request count to `round(rate*duration)` and let Poisson inter-arrival gaps sum to whatever they summed to, so a nominal "10s" run could realize an arrival span of 9.3s or 10.7s — a real mismatch between the duration label and what was actually replayed. `scripts/smoke_bench.py::build_schedule` now generates arrivals until the running sum would exceed the target duration and stops there, so the duration is true by construction and the request count is a reported consequence, not an independent rounded input.)
4. **Evaluation phase**: the frozen rate/schedule set is then run against the held-out corpus for the numbers that go in the pilot writeup. Tuning-phase and evaluation-phase runs are kept in separate `results/` subtrees and never mixed.

Traffic pattern types (each gets its own frozen schedule per rate, per the procedure above):

1. **Steady arrivals** — Poisson or fixed-interval arrivals at each frozen rate.
2. **Sustained load change** — a step change between two frozen rates (e.g., low → high → low), each phase held long enough to reach steady state, to see whether the *winning* configuration changes with load level.
3. **Short bursts** — a brief spike (short run of closely-spaced arrivals) riding on top of a steady baseline rate, to probe short-timescale behavior distinct from a sustained step change.

### 5a. Tuning vs. evaluation split applies to traffic, not just text

A held-out *text* corpus alone doesn't establish that a result generalizes — the arrival pattern/seed is a separate axis that can also be overfit to. So, independently of the corpus split: the random seeds used to generate arrival-time jitter (for Poisson arrivals) and burst placement are drawn from a **tuning seed pool** during calibration/development and a **disjoint evaluation seed pool** for the numbers that get reported. If burst timing or Poisson jitter is tuned by hand while developing the harness, that tuning must have happened only against tuning-pool seeds before evaluation-pool runs are executed.

Each pattern is run against **each of the 4 configs independently first** (no switching) to establish whether different configs win under different traffic (go/no-go criterion 1). Only if that holds does step 6 (transition cost measurement) get run.

## 6. Deadlines

Per the measurement requirements, deadlines must be defined before any policy evaluation. They will be **set empirically from measured single-request service-time distributions** (e.g., a multiple of measured p50/p95 single-request latency under the least loaded config) rather than picked arbitrarily now — arbitrary deadlines chosen before we have real numbers risk being trivially met or trivially missed. This happens right after step 4's baseline single-request measurements, before any of the load-pattern runs in §5 are scored against deadlines.

## 7. What gets recorded per run

- Per-request: scheduled arrival, enqueue-attempt timestamp (recorded even for `REJECTED` requests, not just successful ones — corrected 2026-09-17), enqueue time, execution start, completion time, outcome (§11), which worker served it.
- Per-run: nominal AND achieved arrival rate (§6a corrects a duration/count mismatch that made these diverge), completed throughput with an explicit window definition, p50/p95/p99 latency for e2e/queueing-delay/service-time/generator-delay (all four, not just e2e), deadline miss rate, failures, explicit measurement-window boundaries (run start, first/last scheduled arrival, first/last completion — corrected 2026-09-17, see §6a), request count (**starting point** ≥5,000 requests per steady-state condition — this is a floor, not a guarantee of stable p99; see §12 for how stability is actually checked).
- **Percentile convention (corrected 2026-09-17)**: all percentiles use linear interpolation between closest ranks (numpy's default `'linear'` method — equivalent to Excel's `PERCENTILE.INC`, R's `type=7`), implemented once in `scripts/common/stats.py` and used by every script that reports one. An earlier version used `sorted_values[int(n*p)]` (nearest-rank, biased low) undocumented — on a 200-row W2T4 run this was a 2.2ms difference at p99, large enough to matter at pilot sample sizes. `percentile_method` is recorded in every run summary so this is checkable, not just asserted.
- **Resolved runtime settings, not just intended ones**: each worker reports back the settings it actually applied (`intra_op_num_threads`, `inter_op_num_threads`, `execution_mode`, spinning flags, ORT execution providers) alongside its readiness report, recorded in the run summary — closes the gap between "the config we asked for" and "the config that was verifiably applied" for §8's settings, the same way §8's affinity verification does for CPU pinning.
- Per-run resource accounting: peak RSS per worker process, sampled by actively polling `/proc/<pid>/status` while workers are still alive (corrected 2026-09-17 — reading `VmHWM` after a worker has already exited/been reaped returns nothing, since the `/proc` entry is gone by then; every `peak_VmHWM` value in the pre-fix summaries was null), plus host CPU/mem snapshot before and after, count of idle-but-resident workers if any.
- Run metadata: git commit of the code (recorded automatically in every summary), full config, corpus subset (tuning vs held-out), traffic-seed pool (tuning vs evaluation, §5a), run ID, timestamp, host background-load notes.
- Repetition and variability: see §12.
- Raw per-request logs and run configs preserved (not just aggregates) — written to `results/` as they're generated, one subdirectory per run with a timestamped, git-committed config snapshot.

## 8. Runtime execution settings (fixed and recorded, not left to defaults)

Left implicit, these are exactly the kind of thing that would silently confound a worker/thread comparison — an unrecorded difference in ORT's internal thread behavior or a rogue BLAS thread pool could produce an apparent config effect that's actually a settings artifact. All of the following are fixed explicitly per worker process and recorded in that run's config snapshot:

- **`SessionOptions.intra_op_num_threads`** and **`inter_op_num_threads`** — the two knobs actually varied across W1T8/W2T4/W4T2/W8T1 (§4); `inter_op_num_threads` fixed at 1 for all configs as noted in §4.
- **`SessionOptions.execution_mode`** — fixed to `ORT_SEQUENTIAL` (the default, appropriate for a single mostly-linear embedding graph; `ORT_PARALLEL` is for graphs with independent branches, which this model's graph doesn't really have) and recorded explicitly rather than left as an unstated default.
- **Thread-spinning behavior** — ORT's intra-op thread pool busy-waits ("spins") by default to reduce wake-up latency at the cost of CPU usage. Set explicitly via `session.intra_op.allow_spinning` (and the corresponding inter-op key) in the session config, and recorded. This directly affects both measured latency (spinning helps) and CPU/power usage (spinning hurts) — since higher-worker-count configs (W8T1) put more spinning thread pools on the same 8-CPU budget than lower-worker-count configs (W1T8), an unrecorded default here could itself produce a spurious "more workers is worse/better" effect.
- **CPU affinity is set before session creation, and verified after.** `os.sched_setaffinity` is called on the worker process before `onnxruntime.InferenceSession(...)` is constructed (ORT's thread pool is created at session-construction time and inherits the process's affinity mask at that point — setting affinity after construction would not retroactively constrain already-spawned pool threads). After session construction, the worker inspects `/proc/<pid>/task/*/status`'s `Cpus_allowed_list` for every thread ID under the worker process and logs any thread whose effective affinity differs from the intended set — this is a verification step, not an assumption that setting affinity on the parent process was sufficient.
- **Tokenizer and BLAS thread pools are controlled, not left ambient.** Tokenization is not in the per-request hot path for this pilot (§9), but is used once to build the pretokenized input pool — `TOKENIZERS_PARALLELISM=false` is set (HuggingFace `tokenizers`' Rust-side thread pool otherwise defaults to spinning up threads sized to visible CPU count). Any numpy postprocessing done outside the ONNX graph (masked mean pooling, L2 normalization — see §10) runs with `OMP_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `MKL_NUM_THREADS=1` set in each worker's environment before numpy is imported, so pooling/normalization can't quietly spawn a competing thread pool on top of the CPU budget already allocated to ORT's own threads.

## 9. Timing boundary: what latency does and doesn't include

**Tokenization is excluded from the measured latency for this pilot.** The input corpus is tokenized once, up front (`scripts/pretokenize.py`), producing fixed-length `input_ids`/`attention_mask` arrays; the load generator replays these pretokenized arrays, not raw text. This is a deliberate scope decision, not an oversight: tokenization cost is a real production concern, but folding it in now would mix a roughly-constant-per-request CPU cost into the same numbers as the worker/thread question the pilot is actually about. It can be added as a follow-up dimension later if warranted.

Given that, **measured end-to-end latency = generator scheduling delay + queueing delay + inference/service time**, with three timestamps stamped at precise, implementation-defined points (workers are separate OS processes communicating over `multiprocessing.Queue`, so this is real IPC, not free, and is deliberately attributed to a specific bucket rather than left ambiguous):

- **scheduled arrival → actual enqueue** (`enqueue_ts`, stamped by the generator immediately before `task_queue.put(...)`) = generator scheduling delay. Tracked separately (§5) so generator saturation is visible rather than hidden, and **not** folded into the latency number reported as the server's.
- **actual enqueue → execution start** (`execution_start`, stamped by the worker immediately after `task_queue.get()` returns) = queueing delay. **Caveat, stated rather than hidden**: `multiprocessing.Queue` transit (pickling on the generator side, pipe transfer, unpickling on the worker side) is bundled into this interval and cannot be cleanly separated from genuine "waiting for a free worker" using the stdlib queue — so this number is queueing wait *plus* generator→worker IPC transit. **Correction (2026-09-17)**: the IPC-transit floor is measured by a dedicated, unloaded script, `scripts/measure_ipc_floor.py` — one worker, requests sent one at a time with a gap that exceeds service time so genuine queueing wait is ~0 by construction, isolating IPC overhead cleanly. An earlier version instead reported a loaded run's `queueing_delay` p50 as an "IPC floor estimate," which was wrong the moment the queue actually had depth (observed reporting 37ms and 496ms as "IPC floor" on overloaded runs, which were really queueing wait) — that mislabeled field has been removed from `smoke_bench.py`'s summary.
- **execution start → completion** (`completion_ts`, stamped by the worker immediately after it finishes pooling/normalization — i.e. *before* handing the result to the results queue) = inference/service time: the ONNX Runtime call plus masked pooling/normalization (§10). This deliberately excludes the worker→collector results-queue transit, since that transit is a logging/bookkeeping path the requester never waits on, not part of user-facing latency.
- Reported end-to-end latency per request = `completion_ts − scheduled_arrival_ts` (sum of all three buckets above); each bucket is also retained per-request in the raw log so they can be examined separately, not just as a pooled total.

This boundary is stated explicitly in every run's config snapshot and result summary so a reader can't mistake "latency" here for a number that includes tokenization or generator scheduling slop.

## 10. Correctness verification, including pooling and normalization

Exporting only the transformer backbone to ONNX (see `scripts/export_model.py`) means the **pooling and normalization steps live in our own code, outside the traced graph** — exactly the part of the pipeline most likely to silently diverge from the reference (e.g., an off-by-one in the attention-mask-weighted mean, or a missed/extra L2-normalize step). Verification (`scripts/verify_correctness.py`) therefore checks the **full path**, not just raw ORT output:

1. Load the reference via `sentence_transformers.SentenceTransformer(...)`, and introspect its actual module pipeline (Transformer → Pooling → \[Normalize\]) rather than assuming which post-processing steps it applies.
2. Reproduce the same pooling (attention-mask-weighted mean over token embeddings) and, if present, L2 normalization in numpy, applied to the ONNX Runtime backbone's `last_hidden_state` output.
3. Compare the resulting sentence embeddings, ORT-path vs. reference-path, on a fixed correctness test set (drawn from the tuning corpus, not the held-out set) using both max-absolute-elementwise-difference and cosine similarity, against a tolerance justified for fp32-vs-fp32 numerical differences (not a quantization-level tolerance).
4. The check fails loudly (non-zero exit, explicit report) rather than warning-and-continuing if any sentence falls outside tolerance — correctness is a gate before any benchmarking, per the pilot's own ordering.

## 11. Queue capacity, timeout, and end-of-run drain rules

Every non-completed outcome is counted and categorized — never silently dropped from the results:

- **REJECTED**: the shared queue (§4) has a fixed maximum capacity (`QUEUE_CAPACITY`, set per run and recorded). If the load generator cannot enqueue a scheduled request because the queue is at capacity, that request is recorded as `REJECTED` (with the actual enqueue-attempt timestamp, not just its scheduled timestamp — corrected 2026-09-17) rather than blocking the generator (which would itself distort the open-loop arrival schedule of every subsequent request).
- **TIMED_OUT — corrected 2026-09-17**: the queue-wait check must compare against **actual enqueue time**, not scheduled-arrival time. An earlier version compared `execution_start − scheduled_arrival` against `MAX_QUEUE_WAIT`, which silently folded generator scheduling delay (§9) into what was meant to be a pure queue-wait bound — caught by inspecting a review of the raw log: all 71 `TIMED_OUT` requests in one overload run had exceeded 50ms measured from scheduled arrival, but 39 of those 71 had actually waited *less than 50ms in the queue itself* once generator delay was subtracted out. Fixed: each task now carries its own `enqueue_ts`, and the worker checks `execution_start − enqueue_ts > MAX_QUEUE_WAIT` — a genuine queue-wait bound, independent of generator delay and independent of the deadlines in §6 (this remains a measurement-integrity bound, not the policy under study, and remains a static threshold applied uniformly regardless of config or load, so it doesn't cross into controller territory).
- **UNFINISHED**: at the end of a run's scheduled arrivals, workers continue draining the queue for a fixed `DRAIN_TIMEOUT` (recorded per run). Anything still queued or in-flight when `DRAIN_TIMEOUT` elapses triggers forced worker termination — see the shutdown-accounting correction directly below for how "still incomplete" is actually determined in that case, rather than assumed.
- **Shutdown accounting, corrected 2026-09-17**: making the results-collector thread a daemon (so a corrupted queue pipe after a forced `Process.terminate()` can't hang the whole harness forever — see `research_log.md`) fixes the *hang*, but does **not** by itself establish that every completion record was safely collected before summarizing. Two shutdown paths are now handled differently and explicitly:
  - **Orderly shutdown** (every worker exited on its own before the drain deadline): Python's `multiprocessing.Queue` guarantees a process won't fully terminate until its own queue-feeder thread has flushed everything it `put()` into the pipe, so every enqueued request's result is guaranteed to be *in the pipe* once all workers have `join()`'d. The harness then **actively waits** (`wait_for_collection`, bounded, polling) for the collector thread to actually read all of them, rather than assuming a fixed grace period was long enough. The summary records `orderly_shutdown: true` and `collection_confirmed: true/false` — the latter is a checked fact, not an assumption.
  - **Forced termination** (drain deadline exceeded, workers `SIGTERM`'d with backlog remaining): a killed worker's in-flight `Result` message can be lost in a corrupted pipe even though the worker actually finished the computation. Reconciling "no Result arrived" as blanket `UNFINISHED` would silently misclassify genuinely-completed work as never-started. Fixed by having each worker write directly to shared memory (`multiprocessing.Array`, not the queue) at two points: immediately on dequeue (before inference) and immediately on completion (before queueing the result) — this survives a `SIGTERM` because it's a direct memory write, not a pipe message. Reconciliation for anything missing a `Result` after a forced shutdown now distinguishes four cases instead of one: `UNFINISHED` (shared state shows never dequeued — confirmed), `INTERRUPTED` (shared state shows dequeued but not completed — confirmed mid-flight, true outcome genuinely unknown since it was killed while running), `COMPLETED_UNCONFIRMED` (shared state shows the computation finished locally — its timestamps are recovered from shared memory even though the `Result` message itself was lost), and `TIMED_OUT_UNCONFIRMED` (same idea for a worker that had decided `TIMED_OUT` locally). Each row's `outcome_confirmed` field records whether the outcome came from a `Result` message (confirmed) or was inferred from shared state under a forced shutdown (confirmed for `UNFINISHED`/`INTERRUPTED` specifically, since those readings are direct and unambiguous; `COMPLETED_UNCONFIRMED`/`TIMED_OUT_UNCONFIRMED` are named to make clear the *values* are recovered but the *message* was lost).
- All outcome categories are counted in every run's summary, and raw per-request records retain their outcome label — none are excluded from throughput/latency accounting by omission.

## 12. Run-level variability, not just sample size

≥5,000 requests per steady-state condition (§7) is a starting sample size, not a guarantee that p99 has converged — tail estimates from a single run can still be noisy, and a single number invites false confidence. Handling:

- Each (config × traffic pattern × rate) cell is repeated across **multiple independent runs** (not just one large run), with run order randomized within a session to avoid confounding config identity with thermal drift, host background load drift, or time-of-day effects.
- p50/p95/p99 are reported **per run**, plus the **spread across repeated runs** (e.g., min/max or a simple range across repeats) for each metric — a config isn't reported as "winning" on a tail-latency metric unless the difference holds up across the repeat spread, not just in one run's point estimate.
- If repeat-to-repeat spread turns out large relative to the effect being measured, that is reported as a limitation of the pilot's statistical power, not smoothed over by only reporting a pooled aggregate.

## 13. Transition mechanism (for step 6, only if steps 4-5 show config wins vary by load)

ONNX Runtime does **not** support changing an existing `InferenceSession`'s intra-op thread pool size after construction — thread pool size is fixed via `SessionOptions` at session creation and is immutable for that session's lifetime (verified against ONNX Runtime's documented session/threading API; this is why "transition" can't mean mutating a live session). Two candidate mechanisms will both be implemented and measured, since they have different cost profiles and the brief wants whichever is used to be reported honestly rather than assumed away:

- **(a) Pre-created standby pool**: idle worker processes for each candidate config are already created and warm; a transition means redirecting traffic and (maybe) later killing the old config's workers. Cost is paid up front as idle memory (extra model copies resident) — **but a warm standby pool is not assumed to mean zero transition cost.** Even with workers already alive, a transition can still incur: draining in-flight requests on the outgoing workers before they're killed, first-touch cache effects on the standby workers (a process that's been idle may have cold L2/L3 cache lines and paged-out memory even though its session object exists), OS scheduling/wake-up latency for threads that were idle, and — per §8 — thread-spinning warm-up if spinning was throttled while idle. All of these will be measured during the overlap window where old and new workers are simultaneously resident, including their **combined** CPU and memory footprint during that overlap (not just each config's steady-state footprint separately), since the overlap period is exactly where resource accounting is easiest to undercount.
- **(b) On-demand rebuild**: a transition creates a brand-new worker process (and session) for the target config only when needed, drains the old one, then kills it. No idle memory cost, but pays session-creation + warm-up latency at the moment of transition.

Both get measured end-to-end (draining in-flight requests, process/session startup or wake-up, cache warming, memory for extra copies, thread re-spinning) rather than assumed to be negligible or dominant in either direction.

## 14. Go/no-go checkpoints baked into the ordering

The steps above are ordered so we can stop early if the hypothesis doesn't hold:

1. Run §4 configs × §5 patterns *without* switching → check **go/no-go criterion 1** (different configs win at different loads). If this fails, stop — no point measuring transition costs between configs that never actually trade off.
2. Only if (1) holds: implement §13 mechanisms and measure transition costs → check **go/no-go criterion 2** (costs are material relative to the latency differences from step 1).
3. Only if (1) and (2) hold: assess **go/no-go criterion 3** (room above strong-fixed and simple-adaptive baselines) before building anything resembling a controller.
